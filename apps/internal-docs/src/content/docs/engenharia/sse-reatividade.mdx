## 1. Justificativa Arquitetural: SSE vs. WebSockets

Para manter o ecossistema Aura atualizado em tempo real, optamos por **Server-Sent Events (SSE)** em detrimento de WebSockets. Esta escolha fundamenta-se nos seguintes pilares de arquitetura de software:

### Simplicidade e Portabilidade Local (LAN)
- **Simplicidade do HTTP**: O SSE funciona sobre o protocolo HTTP convencional. Isso o torna extremamente fácil de implementar no backend (usando `ReadableStream` nativos) e no frontend (usando a API padronizada `EventSource`), sem a necessidade de gerenciar handshakes complexos ou bibliotecas adicionais.
- **Execução em LAN**: A simplicidade do SSE permite que o serviço seja facilmente implantado e executado em uma rede local (LAN) ou servidores on-premise na clínica, sem requerer proxies reversos complexos ou gateways de WebSockets que dificultam configurações de intranet.

### Modelo Unidirecional de Atualizações
O fluxo de reatividade da Aura é puramente voltado para a **invalidação de caches de consulta** no cliente (invalidação reativa). 
- O fluxo de dados do **Cliente para o Servidor** é integralmente atendido por chamadas RPC tipadas via **Hono RPC Client** utilizando métodos tradicionais (POST, PUT, DELETE).
- O fluxo de dados do **Servidor para o Cliente** necessita apenas notificar que um recurso foi alterado no banco de dados SQLite (Cloudflare D1).
Dado que o canal de tempo real é estritamente unidirecional, o uso de WebSockets (que é bidirecional) introduziria complexidade desnecessária na gerência de estado e no controle de concorrência.

### Comportamento Computacional e Otimização de Conexões
- **Modelo de Faturamento**: No Cloudflare Workers Paid, a cobrança é baseada em requisições e tempo ativo de CPU. Como a conexão SSE fica ociosa (idle) na maior parte do tempo aguardando eventos, ela não consome ciclos de CPU e não gera custos de processamento contínuo.
- **Multiplexação por Navegador (SharedWorker)**: Embora uma conexão SSE aberta mantenha o contexto da requisição no Worker ativo (segurando o isolado V8 em memória), evitamos o esgotamento de conexões concorrentes no frontend encapsulando o `EventSource` dentro de um **SharedWorker**. Dessa forma, todas as abas abertas no mesmo navegador compartilham a **mesma e única conexão SSE**, distribuindo os eventos localmente via `BroadcastChannel`. Isso reduz o número de conexões ativas na borda na ordem de 5x a 10x.

### Evolução Futura: Durable Objects (DO) e WebSockets
Conforme a aplicação crescer e o número de clínicas/dispositivos simultâneos escalar para milhares de conexões globais concorrentes, a arquitetura poderá migrar para **Cloudflare Durable Objects utilizando a WebSocket Hibernation API**. 
- O uso de Durable Objects com hibernação permite que a Cloudflare gerencie as conexões WebSocket na borda da rede e remova os objetos/isolados da memória quando estão ociosos.
- Isso elimina completamente o consumo de memória persistente e o faturamento de duração de execução para conexões inativas, oferecendo a solução de escala horizontal definitiva para o ecossistema Aura.

## 2. Contrato do Stream (Payload Schema)

A comunicação SSE é estabelecida definindo os headers HTTP adequados e transmitindo mensagens formatadas de acordo com a especificação da W3C.

### Cabeçalhos de Conexão
Para manter o stream aberto e evitar o buffer intermediário de proxies, o backend retorna as seguintes diretivas:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
Transfer-Encoding: chunked
```

### Eventos de Transmissão
Os payloads transmitidos usam o formato padronizado do SSE, estruturado com o tipo do evento (`event`) e o corpo de dados em formato JSON compactado (`data`).

#### Exemplo 1: Invalidação de Agenda
Disparado quando um agendamento é criado, editado ou cancelado. O cliente deve invalidar as consultas da data específica para evitar sobrecarga.

```http
event: INVALIDATE
data: {"entity":"agenda","date":"2026-06-03"}
```

#### Exemplo 2: Atualização de Prontuário de Paciente
Disparado quando um registro clínico é modificado, identificando a entidade e o ID correspondente.

```http
event: INVALIDATE
data: {"entity":"patient","id":"patient_9e472a1b"}
```

## 4. Resiliência e Segurança (Cloud Agnostic)

Para assegurar uma reatividade robusta e segura, o canal de comunicação opera sob as especificações nativas das Web APIs, garantindo portabilidade para qualquer nuvem.

### Falha na Reconexão Nativa e Estratégia Ativa

Embora a especificação da W3C preveja que o navegador gerencie a reconexão automática do `EventSource` nativo, essa abordagem **colapsa** ao utilizar a segurança baseada em **Short-lived Tickets**:
1. **URL Imutável**: O `EventSource` nativo do navegador tenta reconectar automaticamente reutilizando exatamente a mesma URL com a qual foi instanciado (contendo o parâmetro `ticket=...`).
2. **Expiração do Ticket**: Como o ticket expira em 30 segundos, qualquer reconexão automática que ocorra após este período de segurança será liminarmente rejeitada pelo servidor com status de erro (401/403). A API do `EventSource` não fornece hooks nativos para atualizar a URL ou injetar cabeçalhos dinamicamente durante tentativas de reconexão nativas.

Para resolver este limite físico do navegador e garantir alta resiliência, a Aura implementa uma **Estratégia de Reconexão Ativa no Cliente**:
1. **Interceptação de Erro**: O frontend escuta o evento `onerror` do `EventSource` atual.
2. **Descarte Imediato**: Fecha-se a instância ativa de forma explícita via `.close()`.
3. **Resolução de Conectividade (Online/LAN/Offline)**: O cliente tenta obter um novo ticket temporário de conexão via chamada HTTP autenticada:
   - **Modo Online**: Tenta contato com os nós de borda da nuvem da Aura.
   - **Modo LAN (Rede Local)**: Tenta obter do servidor de gateway local ou VPN da clínica.
   - **Modo Offline**: Caso todos os servidores estejam indisponíveis (sem internet ou rede local fora), a reconexão entra em loop de retentativa em background.
4. **Intervalo Resiliente (Backoff Exponencial)**: Para mitigar gargalos e sobrecargas no servidor, as retentativas de requisição de ticket operam sob **Backoff Exponencial**, iniciando em 2 segundos e duplicando sucessivamente até um teto aceitável de 30 segundos (ex: 2s, 4s, 8s, 16s, 30s). Assim que um ticket é obtido com sucesso, o intervalo de backoff é reiniciado para o valor base.
5. **Preservação de Estado (`lastEventId`)**: Ao receber mensagens bem-sucedidas no stream, o frontend atualiza dinamicamente a referência do último ID de evento processado (`lastEventId`). Ao criar a nova instância do `EventSource` com o novo ticket, anexa-se o parâmetro `lastEventId` na URL (ex: `&lastEventId=${lastEventId}`). O backend está configurado para ler este parâmetro da query (caso o cabeçalho HTTP `Last-Event-ID` não esteja presente) e retransmitir eventos que ocorreram durante o período de desconexão.

### Segurança e Validação de Tokens
Diferente de requisições Fetch, a API nativa do `EventSource` do navegador **não permite a definição de cabeçalhos HTTP customizados** (como `Authorization: Bearer <Token>`). Contornamos essa restrição utilizando as seguintes abordagens compatíveis com o padrão:

1. **Short-lived Ticket (Recomendado)**:
   Antes de abrir a conexão, o frontend faz uma requisição HTTP POST autenticada para obter um token de conexão de uso único e tempo de expiração curto (ex: 30 segundos). Este ticket é passado como parâmetro na URL:
   
   ```javascript
   const ticketResponse = await api.auth.sseTicket.$post();
   const eventSource = new EventSource(`/api/stream?ticket=${ticketResponse.ticket}`);
   ```

2. **Validação do Token de Acesso Curto**:
   O token do ticket é decodificado no Worker de borda. Se for válido, a conexão SSE é estabelecida. Caso o Access Token de 15 minutos do usuário expire com a conexão já aberta:
   - A conexão atual permanece ativa (visto que a autenticação ocorreu no handshake).
   - Se a conexão cair, a tentativa de reconexão falhará se o Access Token tiver expirado, forçando o frontend a realizar o fluxo de refresh token silencioso antes de instanciar um novo `EventSource`.

### Exemplo de Implementação Resiliente no Cliente (TypeScript)

Abaixo está o padrão de consumo da API nativa implementado no frontend:

```typescript
import { QueryClient } from '@tanstack/react-query';

interface InvalidationPayload {
  entity: string;
  id?: string;
  date?: string;
}

export function setupRealtimeSync(
  queryClient: QueryClient,
  fetchNewTicket: () => Promise<string>,
  onStatusChange?: (status: 'online' | 'lan' | 'offline') => void
) {
  let eventSource: EventSource | null = null;
  let lastEventId: string | null = null;
  let isClosed = false;
  let reconnectTimeout: ReturnType<typeof setTimeout> | null = null;
  
  // Exponential backoff configuration
  const BASE_DELAY = 2000; // 2 seconds
  const MAX_DELAY = 30000; // 30 seconds
  let currentDelay = BASE_DELAY;

  async function connect() {
    if (isClosed) return;

    try {
      // 1. Fetch a new short-lived ticket (resolves through Online or LAN endpoints)
      const ticket = await fetchNewTicket();
      
      // If we successfully fetch the ticket, we assume we are connected (Online/LAN)
      currentDelay = BASE_DELAY; // Reset backoff delay

      // 2. Build connection URL incorporating lastEventId for event replay safety
      let url = `/api/stream?ticket=${encodeURIComponent(ticket)}`;
      if (lastEventId) {
        url += `&lastEventId=${encodeURIComponent(lastEventId)}`;
      }

      // 3. Close any dangling connection and initialize new EventSource
      if (eventSource) {
        eventSource.close();
      }
      eventSource = new EventSource(url);

      // 4. Handle events and track lastEventId
      eventSource.addEventListener('INVALIDATE', (event) => {
        if (event.lastEventId) {
          lastEventId = event.lastEventId;
        }

        try {
          const payload: InvalidationPayload = JSON.parse(event.data);
          const queryKey = [payload.entity];
          if (payload.date) queryKey.push(payload.date);
          if (payload.id) queryKey.push(payload.id);

          queryClient.invalidateQueries({ queryKey });
          console.log(`[SSE] Cache invalidado para a chave:`, queryKey);
        } catch (err) {
          console.error('[SSE] Falha ao parsear payload de invalidação:', err);
        }
      });

      // 5. Handle connection failures actively
      eventSource.onerror = (err) => {
        console.error('[SSE] Conexão interrompida. Fechando instância e solicitando novo ticket...', err);
        handleReconnection();
      };

    } catch (error) {
      console.error('[SSE] Falha de comunicação ou servidores inacessíveis (Offline). Retentando em breve...', error);
      if (onStatusChange) {
        onStatusChange('offline');
      }
      handleReconnection();
    }
  }

  function handleReconnection() {
    if (eventSource) {
      eventSource.close();
      eventSource = null;
    }

    if (reconnectTimeout) {
      clearTimeout(reconnectTimeout);
    }

    if (!isClosed) {
      console.log(`[SSE] Agendando reconexão em ${currentDelay / 1000} segundos (backoff)...`);
      reconnectTimeout = setTimeout(() => {
        connect();
      }, currentDelay);

      // Double delay for the next attempt, capped at MAX_DELAY
      currentDelay = Math.min(currentDelay * 2, MAX_DELAY);
    }
  }

  // Initial connection trigger
  connect();

  // Return destructor / teardown function
  return () => {
    isClosed = true;
    if (eventSource) {
      eventSource.close();
    }
    if (reconnectTimeout) {
      clearTimeout(reconnectTimeout);
    }
  };
}
```
